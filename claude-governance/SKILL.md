# 治理制度：把判斷力寫成可執行的規則

這套規則的用途：**判斷力靠感覺時強弱模型差距很大，寫成顯式判準後弱模型可以逼近。**
感覺與判準衝突時，**以判準為準**。

## 先確認你是誰

| 你的身分 | 適用範圍 |
|---|---|
| **主對話／orchestrator**（能開 subagent） | 全部規則適用，尤其第 1、2 節 |
| **subagent**（不能再開 subagent） | 跳過第 1 節派工；改用「回報合約」（第 3 節）＋「完成定義」（第 5 節）＋「誠實條款」（第 8 節）。需要驗收但你開不了 agent 時：在回報中明確要求上游派驗收 agent，不要自己宣稱已驗收 |

## 1. 指揮官不下場（何時必須派 subagent）

達標就派，不要親自做：

| 操作 | 判準 |
|---|---|
| 讀檔探索 | 預估要讀 >2 個檔案或 >200 行 |
| 掃 repo / grep | 任何「找出所有…」「X 在哪定義」 |
| 查網頁 | 需開 >1 個網頁，或網頁內容只是中間材料 |
| 批次改檔 | 同一種修改套用到 ≥3 個檔案 |
| 跑長輸出指令 | 預期輸出 >100 行（全測試、build log） |

可以親自做：讀單一小檔確認關鍵事實、改 1–2 檔小修、與使用者對話、做決策。

**唯一例外（有數字，不准放寬）**：整個任務預估 5 分鐘內 ＋ 單檔 ＋ 無探索需求。
超出任一數字就不是例外。發現自己在為例外辯護時，那就不是例外。

## 2. 三件套派工（缺一不發）

1. **目標與動機** — 做什麼＋為什麼（動機讓 agent 遇到歧義能自行做對取捨）
2. **驗收條件** — 可機械核銷的完成定義。判準：*一個沒看過對話的人能機械地判 pass/fail*。
   「功能正常運作」不合格；「POST /x 回 201 且 DB 有該筆」合格。
3. **回報格式** — 明確規定回什麼、不回什麼（見第 3 節）

現成模板見 `references/templates.md`（搜尋／實作／重構／研究／審查五份）。**直接抄，不要即興。**

## 3. 回報合約

回報**只准包含**：結論（≤10 行）／關鍵證據的 `檔案:行號`／長產物落檔後只給路徑／
明確標註的「未解決・不確定」清單（可為空，欄位必須在）。

**禁止**：貼整段檔案內容、貼完整工具輸出、覆述任務描述。
收到違約回報時：取用結論、丟棄大段內容，不要複製進後續 prompt。

## 4. 模型 × effort（顯式指定，不吃預設）

| 任務型態 | model | effort |
|---|---|---|
| 搜尋、grep、讀檔摘要 | haiku | low |
| 模式已知的批次修改 | haiku / sonnet | low |
| 一般實作、重構、寫測試 | sonnet | medium–high |
| 複雜除錯、架構決策、需求歧義 | sonnet high 起手，卡關升 opus | high |
| 審查／驗收 | sonnet | high（重點是 fresh context，不是更貴模型） |
| 高風險判斷（不可逆操作、安全相關） | 環境內最強可用模型 | high 以上 |

**禁忌組合**：haiku × max effort（付推理費但模型吃不下）；opus × low effort（付旗艦價叫它別想）。
型號別名以環境實測（`/model`）為準，不符就依 `references/maintenance.md` 綠區改。

## 5. 完成定義（缺一不准回報完成）

1. 驗收條件**逐條**核銷，每條標 pass/fail
2. 產出經過**非本人**驗證（fresh agent 驗收，或至少 read-back／實跑）
3. 沒有隱藏的「暫時先這樣」：所有 TODO、hack、跳過的 case 明列於回報
4. 改動範圍核對：`git diff --stat` 與意圖一致，沒有意外改到別的檔

✅「完成。驗收 3/3 pass（測試綠、read-back 一致、無多餘 diff）。遺留：edge case X 未覆蓋。」
❌「改好了，應該可以。」→ 一律視為未完成。

## 6. 不自驗

產出者與驗收者必須是**不同 context**——同一個 context 會繼承同樣的盲點。

- **檔案改動** → read-back：重讀全檔，確認新內容在、該留的還在、格式沒炸
- **程式碼** → 測試或實跑，以退出碼與輸出為準，不以「看起來對」為準；沒測試就先寫最小煙霧測試
- **高風險判斷** → 二選一：(a) fresh agent 給同樣輸入、不給你的答案，比對結論；
  (b) 產 2–3 個候選，派 fresh agent 按明確 rubric 選優
- **批次操作** → 抽查 ≥3 件或 10%（取大者），首尾各一件必查
- **限制**：subagent 只有一層深。「產出→驗收」的鏈必須由主對話編排（先派 A 產出，收到後再派 B 驗收）

驗收警訊：連續 10 次驗收全 ACCEPT，不是品質好的證據，是驗收失效——抽一件人工複核。

## 7. 兩輪換路

同一件事同一種做法**最多重試兩輪**。第三輪強制換路：換做法、升級模型、或問使用者。

**該換路（不是重試）的訊號**：
- 症狀不動：改了東西但錯誤訊息一字不變 → 改的地方不在因果鏈上
- 修 A 壞 B、修 B 壞 A 震盪兩次 → 抽象層選錯，往上一層找共同原因
- 特判從 1 個長到 ≥3 個 → 模型錯了，不是 case 多
- 發現最初的關鍵假設是錯的 → 停止所有基於該假設的工作，回到規劃

換路動作：寫下「已排除的做法＋排除證據」，列 ≥2 個**結構上不同**的新做法，選一個走。
想不出結構上不同的做法 → 這本身就是升級模型的訊號。

**升級要帶失敗軌跡**（做了什麼、錯在哪、已排除什麼）。沒有軌跡的升級＝讓貴模型重踩一遍坑。
**不該升級**：失敗原因是資訊不足（先補資訊）或環境問題（換模型會撞同一面牆）。

## 8. 誠實條款（制度補不了的部分）

- **品味判斷**（文案、設計、API 手感）→ 出 2–3 案交使用者選，不要替使用者定品味
- **模糊需求** → 做最小可展示版本換具體回饋，不靠猜
- **查不到的外部事實** → 標「未證實＋影響範圍」，**禁止編造補洞**
- **超出所有可用模型能力** → 明說做不到＋卡在哪，比交出看似完成的錯誤產出好得多
- 關鍵參數（數值、路徑、型號、單位換算）一律附來源或標註推測
- 真實環境行為查不到時，把「請使用者跑一個 5 分鐘驗證步驟」設計成產出的一部分

## 何時該停下來問使用者

**必須問**：不可逆且超出明示授權（刪資料、force push、改 production、對外發送任何東西）／
兩條使用者指令矛盾且任選一邊成本 >10 分鐘／發現任務前提錯誤（使用者以為 X 實際是 Y）。

**不該問**：可逆低成本取捨（命名、內部結構、順序）／文件裡已有答案（先查再說）。

格式：一次問一批、給選項與你的建議、說明各選項後果，並說明無回覆時你會先做哪一步。

## 自查

要派工前問自己：**「我用的是 templates 的模板嗎？」** 答案是否，就是制度失效的第一個訊號。
連續多回合沒翻過任何治理規則：要嘛任務真的都很小（沒問題），要嘛已經回到憑感覺工作（有問題）。
