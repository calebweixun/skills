# 04 — 維護協議：弱模型如何安全更新這套制度

> 這套檔案會腐化：環境會變（新模型、新工具）、教訓會累積、規則會過時。
> 本協議規定誰能改什麼、怎麼改、多久精簡一次。

## 1. 權限分級

### 綠區（模型可自行改，改完在回報中告知使用者即可）
- `references/diagnostic.md` 的「本環境實測結果」區塊：實測到什麼寫什麼。
- `LESSONS.md`：追加教訓（格式見第 3 節）。只准追加，不准刪改既有條目。
- `references/templates.md`：微調措辭、補環境特定欄位。**不准刪三件套欄位**。
- 各檔的明顯事實錯誤：路徑打錯、指令拼錯、模型型號過時（須附實測證據，例如 /model 截圖描述）。

### 黃區（先在對話中向使用者提案、獲同意才改）
- `references/dispatch.md` 的模型×effort 對照表、升降級規則、重試上限數字。
- `references/judgment.md` 的任何判準（這是制度的核心，改壞了全系統跟著壞）。
- `CLAUDE.md` 的鐵律區塊與路由表。
- 新增/刪除治理檔案。

### 紅區（模型永遠不准自行改，即使使用者在單次對話中隨口同意也要再次確認）
- 「不自驗」原則本身。
- 「兩輪上限」原則本身（數字可在黃區調，原則不可廢）。
- 「不可逆操作先問使用者」清單的**縮減**（擴充是綠區，縮減是紅區）。
- 本協議第 1 節（權限分級本身）。

## 2. 修改程序（黃區、紅區確認後皆適用）
1. `cp <file> <file>.bak.$(date +%Y%m%d)` 備份。
2. 動手改。
3. read-back 全檔驗證。
4. 檢查交叉引用：`grep -rn "<改動涉及的檔名或規則名>" ` 確認沒有別的檔還在引用舊內容。
5. 在 LESSONS.md 記一條「制度變更」條目（見下方格式）。

## 3. LESSONS.md 教訓格式（沒有這個檔就建一個）

每條教訓固定四行，多不准少不准：
```
## YYYY-MM-DD [類別: 踩坑|制度變更|環境變更]
情境：一行，什麼任務、什麼條件下發生
教訓：一行，可執行的規則（「以後遇到 X 就做 Y」，不准寫「要更小心」這種空話）
去向：這條是否已升格進正式檔案？[留存於此 | 已併入 <檔名> 第 N 節]
```

**升格規則**：同類教訓出現第 2 次 → 下次觸碰對應檔案時把它升格成正式規則
（綠區檔直接改，黃區檔提案）。升格後原條目「去向」欄改為已併入，不刪原文。

## 4. 精簡排程（防止制度本身變成 token 漏洞）
- 觸發條件（任一達標）：LESSONS.md 超過 **40 條**未升格條目；CLAUDE.md 超過 **60 行**；
  任何治理檔超過 **250 行**。
- 精簡動作：合併重複、把「已併入」的條目搬到 `LESSONS-archive.md`、把 CLAUDE.md 中
  非每回合必需的內容抽成引用檔。
- 精簡屬**黃區**：列出「打算刪/併什麼」清單給使用者過目後執行。

## 5. 環境變更時的維護觸發
- 出現新模型或型號下架：跑 00 檔自查第 3 步，更新實測結果（綠區），
  然後提案更新 01 對照表（黃區）。
- 新裝 MCP/skill/agent：在 00 檔實測區登記（綠區）。若它取代了某條治理規則的做法，提案修改（黃區）。
