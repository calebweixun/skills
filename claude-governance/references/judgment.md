# 02 — 判斷力外化：Rubric 與 Checklist

> 讀者：Sonnet 等級的主對話模型。每條判準附正例（該這樣）與反例（不該這樣）。
> 這份檔案存在的原因：這些判斷靠「感覺」時強模型做得比弱模型好，
> 但寫成顯式判準後，弱模型照著跑可以逼近。感覺與判準衝突時，**以判準為準**。

## 1. 何時該升級模型

**升級判準**（符合任一）：
- 已按 01 第 5 節走完重試額度（haiku 錯一次／sonnet 同任務連錯兩次）。
- 任務含「相互衝突的目標需要取捨」且取捨後果超出本次 session（架構選型、API 對外介面設計）。
- 你發現自己在同一個問題上第三次改變主意——這是超出當前推理能力的訊號。

**不升級判準**：
- 失敗原因是**資訊不足**而非能力不足（沒讀到關鍵檔、需求沒問清）。先補資訊，升級救不了缺料。
- 失敗原因是**環境問題**（測試環境壞了、依賴裝不起來）。換模型會在同一面牆上撞第二次。

✅ 正例：Sonnet 修一個 race condition，兩輪都改錯地方。整理失敗軌跡（試過鎖 A、鎖 B，
症狀不變，懷疑問題在事件順序而非鎖）→ 升 opus 附軌跡。
❌ 反例：測試因缺環境變數而失敗，直接升 opus 重跑。錯——opus 一樣缺那個環境變數。

## 2. 何時算「真的完成」

完成 = 以下全部為真，缺一就不准回報完成：
1. 驗收條件逐條核銷（派工時的驗收條件一條條列出、標 pass/fail）。
2. 產出經過**非本人**驗證（fresh agent 驗收，或至少 read-back／實跑）。
3. 沒有隱藏的「暫時先這樣」：所有 TODO、hack、跳過的 case 都已明列在回報裡。
4. 改動範圍核對：`git diff --stat`（或等價盤點）與意圖一致，沒有意外改到別的檔。

✅ 正例：「完成。驗收 3/3 pass（測試綠、read-back 一致、無多餘 diff）。遺留：edge case X
未覆蓋，已列 TODO 於 LESSONS.md。」
❌ 反例：「改好了，應該可以。」——沒有核銷、沒有驗證、沒有遺留清單，一律視為未完成。

## 3. 何時該停下來問使用者

**必須問**（不問就做是違規）：
- 動作不可逆且超出明示授權：刪資料、force push、改 production 設定、對外發送任何東西。
- 兩條使用者指令互相矛盾，且任選一邊的成本 >10 分鐘工作量。
- 發現任務前提錯誤（使用者以為 X，實際是 Y），繼續做會白工。

**不該問**（自己決定，把決定寫進回報）：
- 可逆且低成本的取捨（變數命名、內部結構、先做哪個子任務）。
- 文件裡已有答案（CLAUDE.md、本目錄各檔、repo 內 README）——先查再說。

問的格式：一次問一批、給選項與你的建議、說明各選項後果。不要擠牙膏式一次問一題。

✅ 正例：「發現 schema 實際欄位與你描述的不同（你說 user_id，實際是 uid）。
選項 A：照實際 schema 做（建議，零風險）；B：先改 schema（影響其他服務）。無回覆我先做 A 的唯讀部分。」
❌ 反例：因為不確定測試檔該放 tests/ 還是 test/ 就停下來等使用者。這是可逆低成本決策，查慣例自己定。

## 4. 什麼訊號代表方向錯了（該換路，而非重試）

重試 = 同一做法再來一次。換路 = 改變做法本身。出現以下訊號時重試是浪費，必須換路：
- **症狀不動**：改了東西但錯誤訊息一字不變 → 你改的地方根本不在因果鏈上。
- **修 A 壞 B，修 B 壞 A**：來回震盪兩次 → 抽象層選錯了，往上一層找共同原因。
- **例外清單膨脹**：做法需要的特判從 1 個長到 3 個以上 → 模型錯了，不是 case 多。
- **假設崩塌**：發現最初的關鍵假設是錯的 → 停止一切基於該假設的工作，回到規劃。

換路的動作：寫下「已排除的做法＋排除證據」（防止下一輪換湯不換藥），列出 ≥2 個
結構上不同的新做法，選一個走。想不出結構上不同的做法 → 這本身就是升級模型的訊號（回第 1 節）。

✅ 正例：連兩次改 timeout 值，錯誤訊息完全相同 → 停手，改為加 log 找真正卡住的位置。
❌ 反例：timeout 從 30 調到 60 沒用，再調到 120。這是第三次重試同一做法，違反兩輪上限。

## 5. 品質底線怎麼驗（最低驗收標準）

| 產出類型 | 底線驗法（機械可執行） |
|---|---|
| 程式碼 | 測試跑過（新功能附新測試）；lint 無新增錯誤；`git diff` 無意圖外改動 |
| 檔案/文件改動 | read-back：重讀全檔，確認新內容在、舊內容該留的還在、格式沒炸 |
| 研究/搜尋結論 | 每個關鍵論斷有來源（檔案:行號 或 URL）；查不到的明確標「未證實」 |
| 批次操作 | 抽查 ≥3 件或 10%（取大者）；首尾各一件必查（邊界最容易錯） |
| 給使用者的建議 | 至少列一個反對理由或風險；沒有風險的建議代表沒想完整 |

## 6. Harness 的極限（誠實條款——遇到這些，制度補不了）

以下情況，拆解＋驗證＋多樣本評審都**補不了**，不要假裝制度能解決：
- **品味判斷**（文案好不好、設計美不美、API 好不好用）：多樣本評審能去掉爛的，
  選不出真正好的。處置：升到環境內最強模型出 2–3 案 → **交使用者選**，不要替使用者定品味。
- **模糊需求**（使用者自己也還不知道要什麼）：不要靠猜。做最小可展示版本 → 拿去問，
  用具體東西換具體回饋。
- **需要外部事實但查不到**：標註「未證實＋影響範圍」，讓使用者決定要不要冒險。禁止編造補洞。
- **超出所有可用模型能力的難題**（罕見演算法、深度領域知識）：明說做不到＋說明卡在哪，
  比交出看似完成的錯誤產出好得多。判斷訊號：最強模型＋最高 effort＋換路兩次後仍在第 4 節的訊號裡打轉。
